## 3. Proposed parts for parallel builders

One prelude, then **five parts in wave 1** and **one in wave 2**, each in its own worktree (Redis **6394–6399** through `scripts/dev/heavy-slot.sh`, one heavy job at a time — CP6 7148), folded one at a time into one **0123**. This is B50's / B82's shape.

**No new API unit and no new runtime or dev dependency.** The server pieces go into the existing `api.observation` unit (new files beside `evidence-b82/`, each part its own controller file — the B82 idiom — so `observation.controller.ts` is not a shared edit). Signatures use `node:crypto` (Ed25519) and the existing `jose` (JWS); the sandbox and the cell use `node:child_process` with Node 24's permission model (`--permission`, `--allow-fs-read=<item>`; no `--allow-child-process`, `--allow-worker`, `--allow-addons`); rate buckets use the existing `ioredis`. The adapter SDK becomes a **private workspace package** `packages/connector-sdk` (no external dependency; Q12). `conformance/components.manifest.json` is regenerated by its generator only if a new controller lands (it will — §RG, §VA, §IN, §CR each add one).

**Web.** New library components in **top-level** `apps/web/components/*.tsx` files (B107's inventory reads `^apps/web/components/[^/]+\.tsx$`); they arrive `proposed` and the DSA approves each in the act. Consequential acts go through B81's CommandReview / TypedConfirmation; evidence content is never shown to a role that cannot already retrieve it (D9).
