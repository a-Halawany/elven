## 1. Build identity — the artifact is built, recorded, carried and verified

`scripts/ops/build-identity.mjs` (new) establishes the identity;
`backup.sh` calls it before anything is dumped, and `restore.sh` refuses to start
a tree whose digest is not the recorded one.

**What the backup does.** It exports the **committed** tree at the current git
SHA with `git archive` (the worktree is never built and never written to),
installs with the committed lockfile (`pnpm install --frozen-lockfile`) and
builds (`pnpm --filter @eye/api... build` — `@eye/api` alone cannot compile, it
needs `packages/contracts`). No test suite is run. Bundle `L` recorded:

```
git sha:        ef85a1283c08617f28d090708a2b750fcf26609f   (worktree clean: false)
                39 uncommitted paths, each listed in MANIFEST.json .build.git.worktree_changes
lockfile:       pnpm-lock.yaml sha256=024f2bbc4debce547f9829027f3701b378b1cc04347f0237a6bdb9189572dfcf (frozen)
toolchain:      node v24.11.1, pnpm 11.9.0 on darwin/arm64
dist digest:    sha256:4bb050f731bb2a38e4cafc1b3e7452c16356cb47f3c6f61cd53af82c437ada83  (367 files, 3,122,464 bytes)
build window:   2026-09-10T22:38:25Z -> 2026-09-10T22:38:32Z (7.6s)
api-dist.tar    4,294,656 bytes (the identified artifact travels with the bundle)
```

**The digest.** Sorted relative POSIX paths, one `"<sha256>  <path>"` line per
file, hashed once. It depends only on contents and relative paths — not on
mtimes, not on where the tree lives. A guard probe proves that directly: the
same bytes copied elsewhere with mtimes forced back to the year 2000 produce the
same digest.

**It is reproducible.** Two independent `git archive` + frozen-install + build
runs of the same SHA produced byte-identical trees
(`sha256:4bb050f7…` both times), and bundle `D`'s independent build twelve
minutes later produced the same digest again from the same SHA.

**The reviewer's original complaint, answered directly.** The old drill *assumed*
that `apps/api/dist` was the build of the checkout. This drill **measured** it —
and the answer changed during the drill, which is the point:

- at backup time, `MANIFEST.json.build_matches_running_dist = false`, with the
  per-file difference recorded in `running-dist-comparison.json`;
- at restore time, the target host's own `apps/api/dist` digested
  `sha256:3feb6d5d84b4adfa9bb33b36f796291245e07ebcaacd0dde3948d2f091ba37c9`
  against the bundle's `sha256:4bb050f7…`.

That is a real divergence — the concurrent session had rebuilt `apps/api/dist`
from its in-progress changes — and `restore.sh` **recorded it explicitly as a
source-to-target upgrade** instead of silently starting it:

```
SOURCE-TO-TARGET UPGRADE, recorded explicitly:
  bundle artifact: git ef85a1283c08  dist sha256:4bb050f731bb2a38e4cafc1b3e7452c16356cb47f3c6f61cd53af82c437ada83
  target artifact: git ef85a1283c08  dist sha256:3feb6d5d84b4adfa9bb33b36f796291245e07ebcaacd0dde3948d2f091ba37c9
  the restore runs the BUNDLE'S artifact, verified above. Running the target's build over this data would be an
  upgrade and must be decided by the operator (docs/ops/BACKUP_RESTORE.md §16), not accepted silently here.
```

Under the timestamp heuristic the old drill used, that rebuilt `dist` would have
been started without a word.

**What restore verifies before it starts anything.** `api-dist.tar` is extracted
into the restore root, re-digested and compared with `MANIFEST.json`:

```
PASS  the artifact carried in api-dist.tar has the digest MANIFEST.json records (sha256:4bb050f7…)
```

and a mismatch is fatal (`REFUSED: … Nothing is started.`). The tree that is
actually started is named in the receipt:

```
starting from: the build root recorded in the bundle (…/builds/20260910T223914Z/src/apps/api)
               — self-contained: the verified dist AND the node_modules of the frozen-lockfile install
```

so the running process is the recorded build *and* the recorded dependency tree.
When the build root is gone, restore falls back to the bundle's own
`api-dist.tar` with the repository's `node_modules`, and then **checks the
repository's `pnpm-lock.yaml` sha256 against the one the artifact was built
with**, reporting a difference.

Refusal is proved in the guard probes rather than only asserted: probe
"a DIVERGENT artifact is refused (exit 1) and the changed path is named" flips
one byte in a stand-in dist and gets `divergent`, exit 1, with `main.js` named.

## 2. Encryption at rest, and a key that is recoverable and never stored

`scripts/ops/bundle-crypto.mjs` (new) seals every payload file;
`backup.sh` refuses to run without `EYE_BACKUP_PASSPHRASE`, and `restore.sh`
refuses a bundle whose passphrase tag does not verify.

**Tooling actually available on this host, checked in the drill's preflight:**

```
openssl: OpenSSL 3.6.4 25 Aug 2026            (/opt/homebrew/bin/openssl)
openssl enc -aes-256-gcm: enc: AEAD ciphers not supported
age: not installed                            gpg: not installed
node crypto: {"cipher":"aes-256-gcm","kdf":{"algorithm":"PBKDF2-HMAC-SHA512","iterations":600000,…},
              "node":"v24.11.1","openssl":"3.6.2","aead_via_node_crypto":true}
```

So the preferred tool (`openssl enc -aes-256-gcm`) **is not usable on this host**
— `openssl enc` has never supported AEAD ciphers — and neither `age` nor `gpg`
is installed. The documented fallback is `openssl enc -aes-256-cbc` plus a
separate HMAC. **That fallback was not used**, for a reason specific to this
script's own constraint that no secret may ever be observable: with a per-bundle
*random* key, `openssl enc` can only be handed that key as `-K <hex>` **on the
command line**, where every process on the host can read it in `ps`. Node is
already a hard requirement of `backup.sh` and `restore.sh` (both refuse to run
without it), its crypto is OpenSSL's own libcrypto, and it provides the AEAD
that `openssl enc` will not — with the key material held only in process memory.
The limitation is therefore stated rather than worked around: **the encryption
is AES-256-GCM through `node:crypto`, not through the `openssl` CLI, because
this host's `openssl enc` cannot do AEAD and its non-AEAD mode cannot take a
key without exposing it.**

**The scheme** (recorded in `MANIFEST.json.encryption`, which stays in the clear
because it holds no secret):

| element | value |
|---|---|
| passphrase | `EYE_BACKUP_PASSPHRASE`, environment only — never a flag, never defaulted, never printed, never written into the bundle |
| KEK | PBKDF2-HMAC-SHA512(passphrase, salt, **600,000** iterations, 32 bytes); 16-byte salt generated **per bundle** |
| verification tag | HMAC-SHA256(KEK, `"eye-backup-bundle/2:verify:" + saltHex`) — a wrong passphrase is refused by this **before any ciphertext is read** |
| DEK | 32 random bytes, generated **per bundle**, in memory only |
| wrapped DEK | AES-256-GCM(KEK, iv, aad `"eye-backup-bundle/2:dek"`) — only the wrapped form is recorded |
| files | AES-256-GCM(DEK, per-file iv, **aad = the file's path inside the bundle**), so a ciphertext cannot be moved to another path without the tag failing |
| per file | iv, tag, ciphertext sha256, plaintext sha256, plaintext bytes |

**What the bundle looks like on disk** — no plaintext survives next to its
ciphertext:

```
MANIFEST.json  RUN.json  api-dist.tar.enc  journal.tar.enc  vault.tar.enc  running-dist-comparison.json
config/env.enc     pg/eye.dump.enc  pg/eye_demo.dump.enc  pg/globals.sql.enc
```

`backup.sh` proves the seal opens before it declares the bundle complete
("verified: every sealed file authenticates and decrypts to its recorded
plaintext sha256").

**Restore, integrity before extraction.** The passphrase tag is checked first;
then every sealed file is authenticated by its GCM tag and decrypted **to a null
sink** to check its plaintext sha256 — nothing is written. Only after the
restore root exists is the payload opened into `<restore root>/plain/` (0700),
never next to the ciphertext, and each decrypted file is re-hashed against
`MANIFEST.json`. Decryption goes to a temporary path and is renamed into place
only after GCM has authenticated the whole stream, so a tampered file never
appears as a readable file at all. Four guard probes pin this: wrong passphrase
refused, absent passphrase refused, right passphrase opens byte-for-byte, one
flipped ciphertext byte → `authentication FAILED` and **no plaintext written**.

**Recovery procedure and the loss case** are in the runbook, §17: to restore you
need the bundle **and** the passphrase; neither is derivable from the other;
if the passphrase is lost the bundle cannot be opened by anyone, including us.

## 3. The NON-EMPTY degraded journal — how the entries were produced

record was written by `apps/api/src/shared/degraded-store.ts` on the
deployment's own code path:

1. `E1` is the isolated environment restored from bundle `L` (its own postgres,
   its own redis, its own vault, its own journal directory under the restore
   root). The live deployment is not involved at any point.
2. **The fault, in `E1`'s database only:**
   `REVOKE EXECUTE ON FUNCTION identity.auth_lookup(text) FROM eye_identity;`

4. **The fault then ends** — the grant is restored — and `E1`'s API is stopped.

## 4. The capture boundary — what it guarantees, and what restore reconciles

The dumps, the vault tar and the journal tar were three separate moments. Both
mechanisms the reviewer offered are now implemented, and the drill used **both**:

- **Recorded boundary + bounded reconciliation** (always). `backup.sh` records a
  boundary on **both** sides of the capture window: per database the current
  snapshot's `xmin`/`xmax` (read with `pg_snapshot_xmin/xmax(pg_current_snapshot())`
  — `pg_current_xact_id()` would assign a transaction id and therefore *write*),
  the audit head per partition, the newest blob manifest and the counts; for the
  vault a listing digest over sorted `"<size> <path>"` lines. Stability is judged
  on what was **admitted**, not on the snapshot markers, which advance with every
  transaction anywhere in the cluster.
- **Quiescence** (isolated sources only). For bundle `D` the isolated API was
  stopped for the whole window, recorded in the manifest as
  `capture.quiesce = "the isolated source's API was stopped for the whole capture
  window; nothing could admit between the first and the last artefact"`.

Both bundles came out coherent, for different reasons:

```
L (live):      capture.stable = true, quiesce = null
D (isolated):  capture.stable = true, quiesce = "…API was stopped for the whole capture window…"
guarantee (both): COHERENT WINDOW: the recorded boundary did not move between the first and the
                  last artefact, so the dumps, the vault tar and the journal tar describe one state.
```

When the boundary *does* move (it did in an earlier run of this same drill, while
the concurrent session's integration suite was writing to the `eye` database),
the manifest says so and the guarantee downgrades to
`BOUNDED RECONCILIATION: each dump is internally consistent (one pg_dump snapshot
per database) and the boundary is recorded on both sides; restore enumerates
everything admitted after boundary_before and reports what falls outside.`

**Restore reconciles against it, row by row:**

```
==> capture-boundary reconciliation: what the source admitted after the boundary the bundle records
  boundary: before the dumps at 2026-09-10T22:39:22Z
  window:   COHERENT — the boundary did not move between the first and the last artefact
  quiesce:  the isolated source's API was stopped for the whole capture window; …
  eye: 1 audit event(s) and 0 blob manifest(s) admitted after the boundary; of the live ones 0/0
       have their bytes in the bundle, 0 do not
  PASS  eye: every row admitted after the capture boundary is enumerated (1 audit event(s), 0 manifest(s);
        0 without bytes in the bundle, named above)
  eye_demo: 0 audit event(s) and 0 blob manifest(s) admitted after the boundary …
```

The single `eye` row beyond a boundary head is **not** window drift: it is the
one pre-existing orphan row above a head that the chain verification also reports
(`frozen_classes: {"chain_broken":17,"noncanonical_bytes":6,"orphan_rows":1}`, all
in frozen partitions with recorded integrity incidents). The reconciliation names
it rather than hiding it, which is what it is for.

The same window rule now governs the count checks. A `pg_dump` takes **one**
snapshot per database at an instant *inside* the window, so a monotonically
increasing counter can legitimately land between the two recorded edges. That is
now accepted and labelled, rather than failed:

```
PASS  eye.audit_events = 62367 — inside the capture window [62362, 62368]
      (the dump's own snapshot instant; the source kept admitting)
```

and chain heads are accepted when every head's `next_seq` lies between the
before-dump and after-dump edge for its partition — with head *consistency*
still proved separately by the `audit.rebuild_chain_heads() would change 0
unfrozen heads` check.

**What it guarantees.** For bundle `D` (and for `L` in this run): a coherent
window — one state across database, vault, journal and configuration. In general:
each dump is internally consistent by `pg_dump`'s own snapshot, the window is
recorded on both sides, and everything admitted after the opening edge is
**enumerated by name** at restore, with its vault bytes checked, so what falls
outside the bundle is a list an operator can act on rather than an unknown.

## 6. The one failing check — a finding about the source deployment

Both restores fail exactly one check, and it is the same one:

```

  {"api":"http://127.0.0.1:3402","ok":false,"at":"admin login","status":401,"code":"EYE-IDN-002",
   "message":"Credential/audience/issuer/device/assurance validation failed",
   "meaning":"the administrator password in the bundle’s config/env is not the credential stored in
              the restored database"}
  FAIL  governed read: login as demo member, evidence list, evidence download with digest re-verified
```

`EYE_TEST_ADMIN_PASSWORD` in `.eye-local/env` — the value the bundle faithfully
copies — is **not** the credential the `platform-admin` principal actually holds
in the database the same bundle dumps. The file was regenerated at
`2026-09-10T18:31Z` (mtime `1789065107`) and the *database roles* were
subsequently brought back into line, but the application principal was not: at
`21:1x` all nine database roles were refused over TCP with the file's passwords,
and by `22:38` seven of nine authenticated (the other two are `NOLOGIN` by
design) while the administrator credential still does not.

This is why a **new check** exists at all. It could not previously be seen by
hand: the postgres image's `pg_hba.conf` **trusts** connections made from inside
the container, so `docker exec psql -U eye_app` succeeds whatever the password
is. `restore.sh` now connects over TCP, where `scram-sha-256` actually applies:

```

  roles restored from pg/globals.sql that can log in: eye eye_app eye_commit eye_identity eye_publisher eye_recovery eye_verifier

  PASS  every LOGIN role restored from pg/globals.sql is opened by the credentials in the bundle's
        config/env (7 authenticated, 0 refused, 0 without a credential in the bundle)
```

The database half of credential recovery therefore **passes**. What remains open
is the **operator credential**: see §8.

## 7. Isolation — and one thing that went wrong

**What the drill did not touch.** `eye-postgres` and `eye-redis` have the same
container ids and the same `StartedAt` before and after; no compose command ran;
`new_project_eye-pgdata` was never named; `.eye-local/env` was not written;
`apps/api/.eye-local/` still holds only its empty `degraded-demo/`; every
isolated container, volume, directory and process was recorded in a `RUN.json`
at creation and removed **by that recorded id**; 0 `eye-restore-*`/`eye-cp45-*`
resources remain. `eurolingo-*` and every other unrelated container was never
named.

**What went wrong, recorded because it did.** Between two runs of this drill, an
ad-hoc cleanup command — `pkill -f 'node dist/main.js'` — was used to clear the
drill's own leftover API processes. That pattern also matched the **live
demonstration API on :3401** (pid 34273, up 23 h 31 m), and killed it. Nothing
else was affected: no container, no volume, no database, no file — only that
process, and only its availability. The demonstration API was running again
(`/readyz` HTTP 200, `{"status":"ok","db":true,"audit":"ok"}`) by the end of the
drill, restarted from outside this work. The drill script itself never used a
pattern kill: it stops each API by the **pid it started** and waits for that
pid's port to be released (`stop_api`), and that is the only shape used in
`scripts/ops/*`.

## 8. What is still open, and what it needs

1. **The operator credential in the bundle does not open the deployment.**
   `EYE_TEST_ADMIN_PASSWORD` in `.eye-local/env` is refused with `EYE-IDN-002` by
   the `platform-admin` principal restored from the same bundle, so the governed
   read (login → evidence list → evidence download with the digest re-verified)
   cannot run, in either restore. The database roles were realigned; the
   principal was not.
   **What it needs, concretely:** either the administrator password that matches
   the credential currently stored in `identity` (the value `.eye-local/env` held
   before it was regenerated at 2026-09-10T18:31Z), or a governed rotation of the
   `platform-admin` credential to the value the file now holds. Until one of
   those exists, no drill can prove the governed-read half of recovery, because
   the bundle genuinely does not contain a usable operator credential. This is
   not something a backup script can fix: it must be repaired in the deployment.
2. **`eye-redis` healthcheck is failing `WRONGPASS`** (failing streak 270 at 5 s
   intervals when observed). The running container's `requirepass` no longer
   matches `EYE_REDIS_PASSWORD` in `.eye-local/env`. The drill never connected to
   `eye-redis` — it only ran `docker inspect` on it — and its isolated redis is a
   separate container. Recorded here as an observation of the live deployment's
   state, same root cause as (1).
3. **A replay/upload source cannot be scheduled.**
   `observation.schedules_to_reconcile()` requires `acquisition_mode = 'live'`,
   so "serve a scheduled tick with no external egress" cannot be done with a
   frozen fixture set — the bound has to be a single named live contract (§5).
   If a zero-egress scheduled tick is wanted as a permanent capability, migration
   0038's predicate is where it would have to change.
4. **The build root is ~1.2 GB per bundle** (a checkout plus its `node_modules`).
   `EYE_BACKUP_PRUNE_BUILD=1` drops the checkout and keeps only
   `BUILD_IDENTITY.json` and `DIST_ENTRIES.json`; the bundle's own
   `api-dist.tar` is then what restore starts, against the repository's
   `node_modules` with the lockfile comparison reported. Retention is the
   operator's call and is documented in §16 of the runbook.
